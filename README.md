# Hunkwell

**Read the patch. Know the result.**

Inspect a single-file unified diff against pasted source text. Hunkwell checks exact positions, context, removals, line counts, and final-newline markers before producing an all-or-nothing result.

## Features

- Parse bounded unified diffs with paired `---` / `+++` headers and numbered hunks.
- Review each hunk's additions, removals, and declared ranges.
- Check forward or reverse without reading or changing any filesystem path.
- Get the first exact conflict, including expected/actual text and newline state.
- Keep resulting text unavailable if any check fails.
- Reverse-check successful results against the supplied source.
- Save editable source/patch projects, resulting text, and inspectable JSON receipts.
- Browser-local processing with no accounts, uploads, analytics, or runtime dependencies.

## Run locally

Node.js 22 or newer. Git is required for the reference tests, not for the browser app.

```sh
git clone https://github.com/KingReaper6940/hunkwell.git
cd hunkwell
npm test
npm run build
npm run dev
```

Open http://127.0.0.1:4187. The preview server serves allowlisted build assets on loopback.

## Use

1. Paste the exact source, including whether it has a final newline.
2. Paste a single-file unified diff. Use **Load example** to try a fictional configuration change.
3. Choose Forward, or Reverse if the source is the patch's newer version.
4. Select **Check patch** and inspect the hunk receipt.
5. If all checks pass and the reverse check restores the source, inspect and save the resulting text.
6. Save an editable project to keep the source, patch, and direction together. Reopen it by pasting its JSON.

Changing an input invalidates the old result. A source conflict returns no partial output. Earlier matched receipts indicate successful checks, not changes made to a file. Header paths are display data and are never opened or executed.

## Accepted format

```diff
--- a/example.txt
+++ b/example.txt
@@ -1,2 +1,2 @@
 first
-old
+new
```

Hunk lines must begin with a space, minus, or plus. Counts must match the body exactly. A count omitted from a range means one line; a zero count identifies an insertion/deletion boundary. Hunks must be ordered and nonoverlapping in the original. New-side positions must agree with preceding changes.

The standard `\ No newline at end of file` marker is supported and checked against the source. `/dev/null` headers require empty original/output text as appropriate. A leading `diff --git` line and optional `index` line are accepted, but other Git metadata is unsupported.

This is a deliberately strict subset of unified diff. It does not implement Git's complete patch format or matching behavior.

## Example artifacts

The [source](examples/source.txt), [patch](examples/change.patch), [result](examples/result.txt), [editable project](examples/project.json), and [receipt](examples/receipt.json) are generated by:

```sh
node scripts/example.mjs
```

The example changes `theme=paper` to `theme=mint`, adds `preview=true`, and verifies that reversing the patch restores the exact supplied source. It is fictional text, not a service configuration.

Project files contain the full source and patch. Successful receipts include the resulting text; conflicts include the relevant expected/actual text. Review exports before sharing.

## Limitations

- LF-only text; CR, NUL, and unpaired UTF-16 surrogates are rejected by the engine. Browser textareas may normalize pasted CRLF/CR to LF before checking, so this is not byte-preserving file import.
- Source, patch, and result each use a bounded 100,000 UTF-16 units; source/patch up to 5,000 lines, output up to 5,000 lines, and at most 100 hunks.
- Editable project JSON is limited to 1,500,000 UTF-16 units.
- No fuzzy matching, shifted-hunk searching, whitespace/case ignoring, three-way merge, partial application, or conflict repair.
- No multi-file, binary, combined merge, mail-format, rename, mode-change, symlink, or Git index operations.
- The app checks supplied text only. It does not contact a repository, prove a file's identity, run code, validate semantics, or determine whether a patch is appropriate.
- Final-newline differences matter. A successful empty output is a valid deletion result, not a failure.
- No automatic storage. Save a project before closing the page. Browser extensions, clipboard, downloaded files, and the hosting environment remain outside the app's control.
- No native download destination, browser interaction, screenshot, or responsive visual verification is claimed for this release. Computer Use timed out waiting for permission to launch Edge. A real screenshot remains pending.

## Checks

`npm test` runs 17 tests. Five generated fixtures are compared against `git apply` in isolated temporary repositories, with LF settings pinned independently of the host's Git configuration. Another check verifies 64 replacement/reverse round trips with and without final newlines. Tests also cover malformed counts, overlaps, range conflicts, source mismatch, empty text, newline markers, project round trips, and unsupported input.

The static build checks module syntax and copies only app assets to `dist/`. CI runs tests and builds with Node 22 and 24 on Windows and Linux. Local HTTP serving was verified. Full browser interaction testing remains pending app access.

## Deploy to Vercel

Import the repository with **Other** as the framework, root directory `.`, build command `npm run build`, output directory `dist`, and an empty install command. These settings are in `vercel.json`. No environment variables, database, server functions, external storage, or paid APIs are needed.

## Format references

[Git's diff-format documentation](https://git-scm.com/docs/diff-format) describes patch output and metadata. [Git apply](https://git-scm.com/docs/git-apply) is a fuller command-line implementation. [Tolerant Patcher](https://github.com/nezarati/tolerant-patcher) offers a different browser workflow with fuzzy matching and shifted-hunk search; Hunkwell keeps checks exact.
